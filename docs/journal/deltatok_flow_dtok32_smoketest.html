Journal — K=32 flow smoke test: a pose-estimation crash, then a dead tokenizer

Smoke-testing the native-K DeltaTok flow (plan) on Jean Zay surfaced two unrelated failures. Both are now root-caused: a real (fixed) robustness gap in DA3 pose estimation, and the actual blocker — the dtok32 tokenizer checkpoint is 100% NaN.

Date 2026-07-07 Target Jean Zay H100 Branch revert Account zuw@h100 Config train_deltatok_flow_jeanzay
Verdict. The native-K flow implementation and the pose-estimation fix are correct — the sanity check runs end-to-end. The only blocker to the K=32 run is that the frozen tokenizer it loads, deltatok_surround_layer12_bsize2_dtok32_cos1e3_1e5_b95/ckpts/current.pth, has diverged to NaN across every weight (both current.pth and current_backup.pth). The K=8 and K=16 sweep tokenizers are finite — the blow-up is K=32-specific. No usable dtok32 checkpoint was preserved.

Failure 1 — DA3 pose estimation crashes on degenerate rays fixed

The sanity check's visualization branch (deltatok_flow_trainer.py:814) decodes the flow-generated tokens with pose_from_depth_ray=True, which asks DA3 to fit a camera pose to the predicted ray map. At the first sanity check the flow ViT is random-init (RESUME=0), so the generated rays are geometrically incoherent. Call chain:

eval_one_epoch:814  pose_flow = self.occ_rae.decode(..., pose_from_depth_ray=True)
  occ_rae.decode:173 → model_da3.inference_batch_from_layer:941 → _process_depth_output:691
    → _process_ray_pose_estimation:614 → get_extrinsic_from_camray → camray_to_caminfo
      → compute_optimal_rotation_intrinsics_batch → ransac_find_homography_weighted_fast_batch:416
        → find_homography_least_squares_weighted_torch:122  →  raise / SVD

Why "<4 points" when the grid has thousands

The homography is not fit on the input grid — it is refit on the RANSAC inliers. Two funnels shrink the full ray grid (N = H·W):

  • z-mask → zero weight (ray_utils.py:40-53): rays with near-zero z (degenerate direction) get weight=0.
  • inlier filter (:387): 100 candidate homographies are scored by points with reprojection error < 3 px; the best hypothesis's inliers are kept for the final refit (:396-418).

On incoherent (untrained-model) rays, no candidate reaches 4 inliers, so the refit gets N<4 and raises. This is downstream of decode, in DA3's head — K-independent (the delta-token count never reaches it).

Moved the failure one frame deeper: those points are near-degenerate, so torch.linalg.svd hit _LinAlgError (ill-conditioned). Reverted — a vendored patch also has to survive re-vendoring and be synced by hand.

    B, V = ray.shape[0], ray.shape[1]

    return c2w, intrinsics
(ValueError, RuntimeError) catches both failure modes (the <4 points ValueError and the SVD _LinAlgError, a RuntimeError subclass); the scope is a single call so it masks nothing else. It returns a real identity pose (not None) of the right shape, so the sanity viz runs as usual. For a trained model the estimate succeeds and this branch is never taken — normal eval is byte-identical.

Isolating the source

Two of the NaN metrics share no compute except one tensor:

  • LossFlow — teacher-forced velocity MSE in token space, no decode, no sampling.
  • LossPointmap_tok — decodes the tokenizer's own reconstruction of the real deltas; never touches the random flow ViT.

Their only common upstream is z, the delta tokens from the frozen dtok32 encode. If z is NaN, every metric above is NaN. Ruled out along the way: the flow ViT (absent from _tok), the t-sampling recipe (absent from _tok), the v-loss weight (clamped: torch.clamp(1-t, min=0.05), deltatok_flow_trainer.py:492), and the pack/unpack (permute only). The encode wrapper (deltatok_shared.py:181-209) is likewise permute-clean — so the NaN is produced inside the frozen tokenizer forward, i.e. the checkpoint itself.

The recent tokenizer-training commits already flag this fight — "switch anti blow-up recipe to cosine LR decay", "suffix run dirs with anti blow-up recipe", "convergence stability". The recipe held at K=8/16 but not at K=32. The ablation's 0.36 was necessarily measured at an earlier, finite epoch that was not checkpointed (only current + current_backup are kept, and both are post-divergence).

What this means

  • Not a native-K bug. The K-axis plumbing, the strict=True load, native-K camera-embed, global attention over S=N·K, the ODE sample, rollout, and decode all work. The wrapper pose guard is a genuine robustness improvement and is worth keeping regardless.
  • The experiment cannot run on dtok32 as-is. Its frozen weights are NaN, so z is NaN, so the flow objective is NaN. No amount of flow-side change fixes a dead tokenizer.
