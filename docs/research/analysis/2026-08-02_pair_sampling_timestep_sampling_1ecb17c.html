DeltaTok timestep sampling: before and after 1ecb17c

The sequence datasets moved from randomly chosen, non-adjacent timesteps labelled with raw stride offsets to one consecutive window labelled 0..k-1. This is what an item actually contains on either side of the change, and what the flow-matching network does with those labels.

2026-08-02 · commit 1ecb17c · measured on Jean Zay against once_processed

The record

Every example below reads the same real record — scene 000000, entry 0 of seq_surround_temporal_sub5_stride9_fs1_once_5cam_all.pkl:

len(seq) = 50 frame indices          # 10 timesteps x 5 cameras
ts       = [0,0,0,0,0, 5,5,5,5,5, 10,10,10,10,10, ..., 45,45,45,45,45]

The layout is timestep-major, camera-minor: entry t*5 + c. ts is the pkl's raw frame offset — this pkl is sub5, so consecutive timesteps are 5 frames apart in the source capture. The ONCE arms set fixed_cams=[0], so only one camera is ever read and an item is one view per timestep.

Before measured

ONCE flow arm at 1ecb17c^: memory_num_views=5, min_num_timesteps=2, no_partial_views=True, reverse_seq=False. _get_views pinned an anchor timestep, drew the rest at random without replacement from the remaining slots, sorted them, and labelled each view with ts[i]:

anchor = num_timesteps - 1 if do_reverse else 0
chosen = [anchor] + list(rng.choice(candidates, size=timesteps_needed - 1, replace=False))
chosen = sorted(chosen, reverse=do_reverse)
times  = [ts[i] for i in memory_view_indices]     # raw stride offsets

Irregular gaps, a different gap pattern every draw, and the label carrying the physical offset rather than a position in the window.

Reversal (reverse_seq=True, 50% chance of a descending window) was on the tokenizer arms, not this flow arm. On a tokenizer item the same block could return [45, 35, 30, 15, 10, 0].

After measured

One ordered, consecutive run at a random offset in the record; labels dense:

start = int(rng.integers(0, avail - self.num_timesteps + 1))     # avail = 10, so start in 0..5
memory_view_indices = [t * max_vpt + c
                       for t in range(start, start + self.num_timesteps)
                       for c in self.cams]
times = [t for t in range(self.num_timesteps) for _ in self.cams] # 0,1,2,3,4

Six real OnceSeqMultiView.__getitem__ calls:

The frame ids show the mechanism: the window slides across the record while the labels the network sees stay [0,1,2,3,4] in every item, uniformly spaced and always forward. The window offset is a sampling detail, not a timestamp.

What the flow network consumes

With cond_mode=delta_ctx_cross and num_ctx_deltas=2 (so n_ctx = 2), num_cameras=1 and V = 5:

timesteprole
0rollout seed — GT tokens, also the frame-0 cross-attn condition
1, 2clean context deltas — GT, no noise, no loss
3, 4forecast — noised, predicted, supervised

Both the loss slice and the visualisation mask are literal arithmetic on those labels:

pred_slice = slice((1 + self.n_ctx) * num_cameras, V)          # slice(3, 5)
ctx_mask   = [batch["timesteps"][b][v] <= self.n_ctx ...]      # t <= 2 is given

Both are correct only because the labels are dense. Under the old ts values — [0, 15, 25, 30, 40] — t <= n_ctx matches the seed alone, and slice(3, 5) indexes positions with no relation to which frames were actually given. That is what the in-code comment at occrae/deltatok_flow_trainer.py:908 records.

How this was measured

  • Before — the sampling block lifted verbatim from 1ecb17c^:occany/datasets/base_seq_dataset.py:303-315 and driven by a real np.random.default_rng over the same record. This re-executes the old algorithm standalone; it is not the old class instantiated in place.
