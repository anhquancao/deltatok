Why — DeltaTok is a delta tokenizer; consecutive frames starve it

Adjacent frames barely change — so there's almost nothing to tokenize

The only change is timestep_sampling in base_seq_dataset.py. Consecutive draws one contiguous run t … t+4; frames are near-duplicates, so the inter-frame delta the tokenizer must encode is tiny and low-rank. Random draws 5 timesteps spread across the whole record — large, varied deltas, the regime the old pair-slice arm trained on.

The trap · degenerate signal

Small deltas = little to learn per step

Consecutive frames in these 10-Hz clips move a few cm. The delta code has to represent almost-nothing, so gradients are weak and the tokenizer inches forward — the loss drifts down roughly linearly instead of dropping.

The fix · restore the large-delta regime

Varied gaps give a rich target

Spreading the 5 timesteps yields big, diverse motion between frames — exactly what a delta tokenizer needs to see to learn structure. Same data, same rig, same cameras; only which timesteps get drawn changes.

Fair by construction: the change is train-only — test_dataset stays consecutive for both arms, so Eval is identical. Random even trains on the harder distribution yet wins on consecutive's home turf.

The tell · latent rank

Consecutive's code is near-collapsed

With tiny deltas there's little to spread over dimensions: PR sits at 1.3 (ep4) → 2.7 (ep8.5). Random's rises to ~35 as it encodes real motion. A rank-2 code is a symptom of a tokenizer with nothing to say.

Honest note: random's ZPartRank at ep 8.5 is a transient peak — it consolidates to ~12 by ep 50 as training settles. The matched-epoch contrast (2.7 vs 35) is the fair read; the point is that consecutive never leaves the floor.
SIGReg is off in both (nosigreg), so this spread gap is pure signal from the data, not a regularizer — isolating the sampling effect cleanly.

The full picture — random keeps converging; consecutive was stopped
