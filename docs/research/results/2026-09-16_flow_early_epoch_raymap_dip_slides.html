What each loss measures
  • LossRaymap = 10 × ray-direction L2 + camera-origin L2 in metres, never rescaled (occany/loss/losses_da3.py:484, gt_scale=True).
  • LossPointmap is in view 0's frame, so a misplaced camera shifts every point.
  • LossDepth is measured from each camera and never sees where it is. It has no dip.
Reading: early on the flow predicts almost no motion, so the forecast camera stops a few metres short. Once it commits to motion it can miss by tens of metres, and L2 in metres weighs those misses heavily.

Findings

The early raymap dip is a camera that does not move, not a better flow.

1
Only pose-dependent losses dip. tc1536 raymap 3.77 / 3.81 at ep 0–1, 10.52 at ep 2, 5.63 at ep 43; pointmap 5.00 / 4.98 → 11.52 → 8.28. Depth, measured per camera, has no dip (4.17 → 4.40 → 3.75).
2
At ep 0–1 the forecast cameras stop short. The camera path is 0.53–0.72× GT length on all 6 moving val scenes; t2–t4 draw on top of each other.
3
At ep 2 it overshoots. 3 of 6 scenes run 1.49–3.16× GT length; on 105263 the path reaches 49 m, where GT ends near 16 m. By ep 43 all 6 sit at 1.13–2.42×.
4
The loss follows the path error. Mean path error 5.7 / 5.6 / 16.9 / 7.3 m at ep 0 / 1 / 2 / 43, against raymap 3.77 / 3.81 / 10.52 / 5.63. Camera origins enter the loss as L2 in metres, so a few large misses dominate the mean.
So what. The decoded losses reward not moving the camera. A flow that has learned nothing about motion reads better than one that commits to it, which is QUESTION 20's worry about ranking flows by these losses.
Caveat · path length is a proxy. It is the bounding box of the 5 cameras, read by eye from each panel's window (window = 1.5 × path). It is not a per-frame position error.
Caveat · coverage. tc1536 only, 8 logged scenes (6 moving), epochs 0 / 1 / 2 / 43. The losses average all 128 val sequences.
