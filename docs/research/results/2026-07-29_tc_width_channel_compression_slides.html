The setup — two ways to spend the same floats

Two compression axes, one budget

A delta code is K tokens × Cz channels per camera per frame transition. Halving either halves the budget. We wanted the channel axis because the flow model's output dim is the per-token Cz.

Why Cz and not K? flow OUT_DIM = per-token Cz — a smaller, decorrelated target is easier to model. Flow compute is d_model/token-count bound, so Cz buys modelling ease, not speed.

Attempt 1 — a single Linear down/up

Equal floats, 7× the loss

Against the equal-budget control the channel squeeze converges ~5× worse, and ~7× worse than uncompressed. Not instability — zero loss spikes, no grad-skips fired. It simply converges to a much worse optimum.

Equal latent float count ≠ equal optimization difficulty. DA3 layer-12 features are not naturally low-rank, so one shared linear subspace is the expensive way to spend the budget.

Interlude — what SIGReg actually measures · LeJEPA, Balestriero & LeCun 2025

Ask every random 1-D shadow to be a standard normal

Cramér–Wold: isotropic Gaussian ⟺ every 1-D projection is N(0, 1). So sketch it — K random directions, each marginal scored by its characteristic function.

Why we reached for it: the tc768 code was using a fraction of its 768 dims, and a Gaussianized latent is also an easier target for the downstream flow. No covariance matrix is ever formed. Illustrative — 2-D analytic sketch, not measured data.

φ̂k(t) = 1⁄S Σi e i t ⟨zi, ak⟩  — the marginal enters only here
statk = ∫0 t_max |φ̂k(t) − e−t²/2|² e−t²/2 dt · loss = meank
Knobs: num_slices 2048 — variance of the estimate · t_max 3.0 — which frequencies get compared · knots 17 — quadrature resolution · weight 0.05 — pressure against recon. We drop the classical × N scaling, so our values do not compare to LeJEPA's λ — and statₖ is where their clip_value would gate.

Attempt 3a — SIGReg, and why the first try measured nothing

The regularizer was reading its own noise floor

If the code collapses into a few directions, push it back toward N(0, I). But the estimator saw S = 128–256 rows of dim 768 — a third of the dimensions it was asked to characterize.

Attempt 3b — weight and geometry

Then: 20× too strong, in the wrong geometry

With a working estimator, weight 1.0 de-collapsed the latent and cost 82% of KITTI recon. Two corrections bought the win: drop the weight to 0.05, and remove the z-LayerNorm that made SIGReg's target unreachable.

Why the z-LayerNorm had to go (_nozn)

The non-affine LayerNorm(768) pins every token to ‖z‖ = √768, so the radial component of an N(0, I) target is structurally unreachable — SIGReg was asked to match a distribution the architecture forbids. It was not the cause of the collapse: participation rank 44.55 → 45.24 across it.

Summary — capacity, reconstruction, and what survives downstream

The squeeze costs 2.9× in reconstruction — and nothing measurable downstream.

Rail = the budget. SIGReg lifts utilisation 10×, to 22.5% — level with uncompressed 21.6%. The 1.9× deficit is just the 2:1 Cz. Whitening does not add capacity — it is an invertible per-channel rescale, yet it nearly doubles the same code's PR.

Reconstruction is where the squeeze is punished — 2.9× the uncompressed loss, and dtok32 still wins at equal float budget.

Flow-matching forecast, decoded to depth. Faint = each tokenizer's own ceiling. The 11% ceiling gap vanishes: both land at ~5.7.

What it adds up to
  • Utilisation was never the problem. Both codes fill ~22% of their channels; the squeeze simply has half as many.
  • The reconstruction penalty is real — 2.9×, and token reduction beats it at equal budget.
  • It does not propagate. Decoded depth 5.66 vs 5.72. The flow's own error (~5.7) swamps the tokenizer gap (2.70 vs 2.44) — downstream, the flow is the bottleneck, not the code.

Whitening — does 3.7× the effective dims buy a better flow?

No. Whitening moves the metric, not the code.

Same checkpoint, same tokens. Per-slot (K,C) z-scoring flattens the spectrum, and PR reads 1.9× higher.

What a predictor reaching for zero context already scores — a model with conditioning beats it (this arm: 0.575). Flow noise is isotropic and the loss is a flat per-channel MSE, so inflating the near-empty directions to unit variance turns free constant targets into full-difficulty ones.

The higher-PR arm is not the better one. PR annotated at right; the two land within 1% of each other.

Why it can't work
  • It is already whitened. The comparable dtok64 flow run sets model.whiten_stats=latent_stats_waymo_pos.pth — PR 638.8 is the code that flow actually saw, and it did not win.
  • Invertible ⇒ no information added. A diagonal rescale the decoder undoes exactly. PR moves only because it is invariant to rotation and global scale, but not to a per-channel one.
  • It does change the loss — floor 0.80 → 1.40. Higher Eval/Loss, identical content: the other reason cross-arm Eval/Loss is not one scale.
  • Missing ablation: every dtok64 flow slurm sets whiten_stats. A no-whiten arm would separate it from the tokenizer.
