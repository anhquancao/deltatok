DeltaTok channel-bottleneck diagnosis

Why the 768-channel tc768 bottleneck fails, and what fixes it · 2026-07-24

Verdict: mixed — mostly optimization

Problem. At an equal latent budget (49,152 floats/token-set), squeezing each delta token's channels 1536→768 (tc768) plateaus at recon 0.065 — ~7× worse than the uncompressed tokenizer (0.0092) and ~4× worse than reducing the number of tokens instead (dtok32, 0.018) at the same budget.

Diagnosis. A PCA-projection roundtrip through the frozen decoder shows the failure is dominantly an optimization problem: a trivial PCA projection to 768 dims already reconstructs at 0.023 — 2.8× better than the trained bottleneck's 0.065. The from-scratch bottleneck cannot even find that subspace. On top of that sits a real but secondary linear-capacity floor: 768 dims hold only 84.4% of the variance, so a linear map caps at 0.023 (~2.5× the 0.0092 ceiling).

Fix (in progress). Train a nonlinear MLP bottleneck from scratch (participation-rank ~290 « 768, so the capacity is there if the map can curve). Watch the step 3–5k breakthrough; if it survives, the optimization blocker remains and the next step is an α-annealed warmup.

1. The problem: channel vs token compression at equal budget

A delta token can be compressed on two axes: K (number of tokens per camera) and Cz (channels per token). They carry the same float budget but are not interchangeable for optimization. Reducing K keeps every surviving token a free, full-rank 1536-d vector. Reducing Cz forces all tokens through a single shared low-rank linear map — and the DA3 layer-12 features are not naturally low-rank.

2. Pre-norm fixes gradients, not capacity

The affine pre-bottleneck LayerNorm (bottleneck_pre_norm) that tamed an earlier ~60× gradient amplification helps — ~15% lower eval and far steadier — but it does not move the plateau. The run is stable; it simply converges to a much worse optimum.

3. The diagnostic: capacity vs optimization

Method (diagnose_deltatok_bottleneck.py, no training): take the frozen uncompressed dtok64, (A) PCA its delta tokens, and (B) project each token onto its top-r PCA subspace and feed it through the frozen decoder, measuring recon per rank. Explained variance is a proxy; recon-after-roundtrip is the real test.

A. Eigenspectrum

Participation-ratio effective rank = 290 / 1536 — the intrinsic dimensionality is well under 768, but the variance has a heavy tail, so a linear 768-subspace keeps only 84.4%.

Three levels at Cz=768: 0.0092 (uncompressed ceiling) → 0.023 (naive PCA projection) → 0.065 (the trained bottleneck).

  • Mostly optimization. The trained bottleneck is 2.8× worse than a trivial PCA projection — it can't find the linear-PCA-quality subspace (the blocked "coordination event").
  • Secondary linear-capacity floor. A linear 768 map tops out at ~0.023 (84% variance); reaching the ceiling with a linear map would need ~1280 dims.
  • The capacity is there. Participation rank ~290 « 768 — only a nonlinear map (or a modestly larger Cz) can fold the low-energy tail into 768 dims.

4. The fix

Chosen path (from scratch, no dependency on a stored uncompressed checkpoint): a 2-layer SiLU MLP bottleneck instead of a single Linear, via the new model.deltatok.bottleneck_mlp flag — down H→H→z_dim, up z_dim→H→H. It attacks the linear-768 capacity floor; the curved manifold can exceed the 0.023 linear cap toward the 0.0092 ceiling at fixed Cz=768.

Honest caveat. The MLP targets capacity, not the dominant optimization blocker — a random MLP is more lossy at init, so it may plateau like tc768. Watch the step 3–5k breakthrough on Train/LossRecon: drops toward ~0.02 ⇒ the MLP alone worked; stays ~0.06 ⇒ the optimization blocker survived ⇒ add an α-annealed full-rank warmup (form the code at full rank first, then fade the compression in).
